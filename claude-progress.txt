## 2026-08-16 17:02 — Feature #1: Core error taxonomy and Result-style types for the kernel

### What was done:
- Added src/core/errors.ts: abstract AppError base class (extends Error) with a stable machine-readable code, a default HTTP statusCode, a safe overridable publicMessage (separate from the internal Error#message), optional structured details, and an internal-only cause (never serialized). Four concrete subclasses: ValidationError (400/VALIDATION_ERROR), ConfigError (500/CONFIG_ERROR), PluginLoadError (500/PLUGIN_LOAD_ERROR), CapabilityDeniedError (403/CAPABILITY_DENIED), each with its own safe default public message.
- toJSON({ includeStack }) serializes to an API error envelope shape { code, message, details?, stack? } — stack omitted unless includeStack is explicitly passed. Added isAppError() type guard and toErrorEnvelope(error, options) to collapse any unknown thrown value (plain Error, thrown string, etc.) into a generic non-leaking INTERNAL_ERROR envelope for the kernel's top-level error isolation path.
- Added src/core/types.ts: Result-style type (Ok<T> | Err<E>, default E = AppError) plus ok(), err(), isOk(), isErr(), unwrap(), unwrapOr(), mapResult(), mapErr() helpers for kernel operations that fail without throwing.

### Testing:
- tests/core/errors.test.ts (24 cases): per-subclass code/statusCode assertions, default public messages proven not to contain injected internal secrets/identifiers, explicit publicMessage override, internal message vs publicMessage independence, structured details round-trip, cause kept internal-only and absent from JSON.stringify output, toJSON() envelope shape exact-match with no stack key by default, stack included only when includeStack:true, toErrorEnvelope() behavior for AppError/plain Error/thrown string.
- tests/core/result.test.ts (9 cases): ok/err construction + isOk/isErr narrowing, unwrap returning value vs throwing the wrapped error, unwrapOr fallback, mapResult/mapErr transforming the correct branch and passing the other through untouched.
- Ran npm run build (tsc strict, incl. exactOptionalPropertyTypes/noUncheckedIndexedAccess) — clean. npm run lint (eslint) — clean. npm test (vitest) — 3 files / 33 tests passing (includes pre-existing smoke test). npx prettier --check on all new/changed files — clean.

### Notes:
- Kept AppError abstract so every thrown instance is forced through a concrete subclass with a real code; add new error kinds by extending AppError with a fixed code/statusCode and an overridden defaultPublicMessage(), not by instantiating AppError directly.
- publicMessage is intentionally separate from Error#message: message can carry internal detail for logs (file paths, plugin ids, SQL fragments) since it is never included in toJSON(); only publicMessage/code/details cross the API boundary.
- cause uses the native ES2022 Error cause option (supported by tsconfig lib ES2022) and is deliberately excluded from toJSON()/serialization — read it via error.cause for internal diagnostics/log correlation only.
- Result<T, E = AppError> lives in types.ts (not errors.ts) per spec.md's directory layout, and imports AppError only for the default type parameter — no runtime coupling.
- Gotcha for future agents: passing a variable already typed as the Result<T,E> alias into mapResult/mapErr can make TS fail to infer the callback parameter type (falls back to unknown) even though passing ok()/err() calls directly infers fine — annotate the callback parameter explicitly in that case (see result.test.ts) rather than trying to force generic type args onto ok()/err(), which only take one type parameter each.
- Next natural consumer: feature #4 (plugin manifest zod validator) will want ValidationError; api-gateway (later) will want toErrorEnvelope()/AppError#toJSON() for its error-envelope middleware.

## 2026-08-16 17:08 — Feature #2: Layered configuration system (defaults -> env -> operator overrides) validated with zod

### What was done:
- Added src/core/config.ts: generic loadConfig(schema, {defaults, env, overrideFilePath}) engine that merges three layers (defaults -> process.env -> optional local JSON override file) in that precedence order and validates the merged object with a zod schema, matching spec.md's 'validated per-plugin against a zod schema the plugin exports'. Env values are filtered to only the schema's own keys (via schema.shape) before merging, so process.env's hundreds of unrelated vars never leak in. The override file is fully optional — a missing path/file is a silent no-op, not an error; malformed JSON or a non-object top level throws ConfigError.
- Added CoreConfigSchema (zod object: NODE_ENV enum development/test/production default development, PORT z.coerce.number().int().min(1).max(65535) default 3000, LOG_LEVEL enum fatal/error/warn/info/debug/trace default info) plus loadCoreConfig() as the kernel's own instance of the generic loader, and the CoreConfig type alias.
- Validation failures are normalized into a single human-readable ConfigError message (formatZodError) rather than a raw ZodError — e.g. missing required field says '<path> is required but was not set (checked defaults, environment, and override file)'; other failures render as '<path>: <zod message>'. Full ZodError issues are attached as ConfigError.details for programmatic consumers, and the original ZodError is preserved as cause. ConfigError's default publicMessage ('The server is misconfigured.') deliberately never includes the internal field-level detail.
- Added config.local.json to .gitignore as the documented convention for the operator override file, alongside .env.

### Testing:
- tests/core/config.test.ts (13 cases): missing required var throws ConfigError with a message naming the field and confirming all three layers were checked, and that the internal detail is absent from publicMessage; multiple required fields with only one satisfied still fails; CoreConfigSchema loads correctly from defaults alone and from env alone (PORT string '8080' coerced to number 8080); invalid NODE_ENV enum and out-of-range PORT both rejected; full precedence suite proves env overrides defaults, override file overrides env (which overrides defaults), a missing override file silently falls through, and a combined test exercises all three layers across distinct fields (PORT via env-over-default, LOG_LEVEL via file-over-both, NODE_ENV via default-only) in one call; malformed JSON and non-object JSON in the override file both throw ConfigError.
- Ran npm run build (tsc strict) — clean. npm run lint (eslint) — clean. npm test (vitest) — 4 files / 46 tests passing (13 new + pre-existing 33). npx prettier --write/--check on the two new files — clean (pre-existing formatting warnings in AGENTS.md/feature_list.json/spec.md are unrelated, untouched by this feature).

### Notes:
- loadConfig() is intentionally generic (schema: ZodObject<Shape>) rather than hardcoded to CoreConfig, per spec.md's per-plugin config requirement — future plugins (database-mysql, api-gateway, etc.) can call it directly with their own zod schema instead of duplicating merge/validate logic. loadCoreConfig() is just loadConfig() pre-bound to CoreConfigSchema.
- Env-key filtering relies on Object.keys(schema.shape), which requires the schema to be a ZodObject (not an arbitrary ZodTypeAny) — LoadConfigOptions is typed accordingly (schema: ZodObject<Shape>). If a future plugin needs a non-object root schema, loadConfig will need a variant.
- Chose to keep config.ts free of filesystem side effects beyond the explicit, opt-in overrideFilePath (no implicit default path, no dotenv.config() call) so it stays a pure function of its inputs and is trivially testable without mocking the environment — tests always pass an explicit env object rather than relying on ambient process.env (vitest sets NODE_ENV=test, which would otherwise leak into assertions).
- dotenv is already a dependency (package.json) but not wired up anywhere yet — that belongs to the server bootstrap feature (src/server/index.ts is still the documented placeholder), which should call dotenv/config() before invoking loadCoreConfig() so .env-file values land in process.env and flow through the env layer. Not done here to keep this feature's scope to the config module itself.
- Next natural consumer: the kernel bootstrap feature should replace src/server/index.ts's ad-hoc 'Number(process.env.PORT ?? 3000)' with loadCoreConfig(), and any plugin manifest/config work can reuse loadConfig() with its own zod schema.

## 2026-08-16 17:18 — Feature #3: Structured logger with automatic secret redaction

### What was done:
- Added src/core/logger.ts: createLogger({ level, context, stream }) wraps pino to emit structured ndjson with a base context (pid, hostname, plus caller-supplied fields like plugin/requestId) merged into every line; withContext(logger, context) derives a child logger that layers further context (e.g. per-request requestId) on top without losing the parent's.
- Implemented deep, unconditional secret redaction: redactSecrets()/redactValue() recursively walk any object/array (with circular-reference guarding via WeakSet) and replace the value of any key matching REDACTED_FIELD_NAMES (password, secret, token, apikey, authorization — case/punctuation-insensitive substring match, so API_KEY, apiKey, x-api-key, accessToken, Authorization all match) with REDACTED_PLACEHOLDER ('[REDACTED]'). Wired in at three points so nothing bypasses it: base context passed to createLogger(), bindings passed to withContext()/child(), and every individual log call's merging-object/Error argument via pino's hooks.logMethod (which fires for child loggers too, confirmed empirically).
- Special-cased Error values: redactError() clones via Object.create(prototype) to preserve the original class (so pino's err serializer still reports the correct type, e.g. ValidationError/UpstreamError) and message/stack, while redacting any secret-like own enumerable property (e.g. a mistakenly attached err.apiToken); cause is intentionally dropped from the clone rather than redacted imperfectly. Left Date/RegExp/Map/Set/typed-arrays/Buffer and any value exposing its own toJSON() untouched (returned as-is) so redaction never corrupts values that manage their own JSON representation.

### Testing:
- tests/core/logger.test.ts (28 cases) using an in-memory Writable capturing stream (pino writes to it synchronously, confirmed empirically) so tests assert on the exact raw ndjson pino would emit, not a mock: structured JSON output with plugin/request context merged in (createLogger context, withContext layering, per-call fields alongside persistent context); redaction proven for all 5 field names across case/punctuation variants (password/Password/PASSWORD/userPassword, secret/clientSecret, token/accessToken, apikey/apiKey/API_KEY/x-api-key, authorization/Authorization) both via raw-string absence of the secret value (raw().not.toContain(secretValue)) and via the parsed line showing REDACTED_PLACEHOLDER; secrets nested arbitrarily deep in objects/arrays; a secret-like property attached to a thrown Error while message/stack/type are preserved; secrets in base context and in withContext() bindings; secrets never leak across repeated calls on the same logger. Plus direct unit coverage of redactSecrets(): every declared field name, non-secret fields untouched, input not mutated, circular references handled, Date and custom-toJSON values left opaque.
- Ran npm run build (tsc strict) — clean. npm run lint (eslint) — clean. npm test (vitest) — 5 files / 74 tests passing (28 new + pre-existing 46). npx prettier --check on the two new files — clean (pre-existing AGENTS.md/feature_list.json/spec.md warnings are unrelated/pre-existing, per feature #2's notes).

### Notes:
- Deliberately did NOT use pino's native path-based redact option (fast-redact) as the primary mechanism — it requires the caller to enumerate exact paths in advance (e.g. 'req.headers.authorization'), which can't guarantee an arbitrary, unknown-shape log call is safe. Instead built a recursive deep-redact walk keyed purely on field *names*, wired in via pino's hooks.logMethod (verified this hook receives the raw, pre-serialization first argument — including a raw Error before pino's internal err-wrapping — and that it fires on child loggers too, not just the root logger) plus explicit redaction of context/bindings at createLogger()/withContext() call sites (which bypass hooks.logMethod entirely since they aren't a 'log method call').
- Key design tradeoff future agents should know: redactValue() only reconstructs plain objects, arrays, and Errors; anything with its own toJSON() (or Date/RegExp/Map/Set/typed arrays) is returned untouched rather than descended into, so a class instance with a custom toJSON isn't corrupted by losing its custom serialization — but this also means a secret-like field nested *inside* a custom-toJSON object's internals would not be redacted. This is an intentional, documented scope boundary, not an oversight.
- Next natural consumers: the kernel's Capability/Permission Broker and RBAC plugin's audit log (spec.md: 'every capability grant, permission check, and mutating action is logged with actor/target/outcome') should use withContext() to attach actor/target/outcome fields; api-gateway's Fastify bootstrap should replace the placeholder 'logger: true' in src/server/index.ts with createLogger()/loadCoreConfig()'s LOG_LEVEL once the kernel bootstrap feature lands, so request logs get the same redaction guarantee instead of Fastify's bare pino default.

## 2026-08-16 17:24 — Feature #4: Plugin manifest schema (plugin.json) and zod validator

### What was done:
- Added src/core/manifest.ts: PluginManifestSchema (zod, .strict() at every object level) defining plugin.json's shape per spec.md — id (lowercase-kebab-case, regex-validated), version (canonical SemVer 2.0.0 grammar via a strict regex matching semver.org's own reference regex — deliberately NOT semver.valid(), which is a loose parser that accepts a 'v' prefix and silently strips build metadata from its output), depends_on (Record<pluginId, semverRange>, defaults to {}, validated with the 'semver' package's validRange() since range grammar — comparator sets, hyphen ranges, x-ranges, ||, — is impractical to hand-roll correctly as a regex), capabilities.provides/capabilities.requires (string arrays following a 'namespace:action' grammar, e.g. db:query/http:route/rbac:check, each defaulting to [], with a superRefine pass that flags duplicate entries within a single list — cross-list overlap between provides and requires is explicitly allowed), and entry_point (relative path regex: no leading '/', no '..' traversal, must end in .ts/.js/.mjs/.cjs).
- Added validateManifest(input: unknown): Result<PluginManifest, ValidationError> — never throws; uses schema.safeParse() (which does not short-circuit) so every violation in the input, not just the first, is collected into a typed ManifestValidationIssue[] ({ path, code, message }) and attached at ValidationError.details.issues, with a human-readable summary of all violations as the internal message (publicMessage stays the generic 'The request was invalid.' from errors.ts, so manifest content never leaks to an API caller). Custom zod issues (duplicate capability) and .strict()'s unrecognized_keys are both mapped to stable machine-readable codes ('duplicate_capability', 'unknown_field') alongside zod's own issue codes.
- Added 'semver' (^7.8.5) as a direct dependency (previously only present transitively) and '@types/semver' as a devDependency — used for depends_on range validation only; version format validation uses a hand-matched official regex instead, see Notes.

### Testing:
- tests/core/manifest.test.ts (36 cases): 7 valid-manifest cases (full manifest, minimal manifest with depends_on/capabilities defaulted, multi-segment id, prerelease+build-metadata version, a spread of valid range syntaxes — ^, ~, >=..<, x-range, '*' — in depends_on, nested entry_point path, empty provides/requires arrays); bad semver (5 variants: '1.2', 'not-a-version', '1.2.3.4', 'v1.2.3', '' via it.each, plus a dedicated case asserting the error names the 'version' path and publicMessage stays generic); missing id (field entirely absent, and empty-string id); duplicate capability (within provides, within requires, plus a case proving the same capability in both provides AND requires is NOT flagged as duplicate); malformed capability grammar (7 variants via it.each: no colon, empty action segment, empty namespace segment, double colon, 3+ segments, uppercase, space-instead-of-colon); unknown field (top-level, and nested under capabilities); plus additional invalid variants covering malformed depends_on range, uppercase/underscore plugin id, absolute and directory-traversal entry_point, unsupported entry_point extension, non-object input, missing entry_point, and one case asserting ALL violations in a single malformed manifest are collected (not just the first).
- Ran npm run build (tsc strict) — clean. npm run lint (eslint) — clean. npm test (vitest) — 6 files / 110 tests passing (36 new + pre-existing 74). npx prettier --check on the two new/changed files — clean.

### Notes:
- Chose depends_on as Record<pluginId, semverRange> (mirrors package.json#dependencies) rather than an array of {id, range} objects — cleaner JSON shape, and it structurally rules out duplicate dependency entries for free (JS/JSON object keys are unique), so the 'duplicate' requirement in this feature's steps only needed custom superRefine logic for capabilities.provides/requires, which ARE meaningful ordered lists where duplicates are a real, detectable mistake.
- Gotcha for future agents: semver.valid(value) is NOT a strict/canonical-format check — it's lossy (drops build metadata) and lenient (accepts a leading 'v'). If you need to validate that a string IS canonical SemVer 2.0.0 (not just parseable-ish), match it against the official regex published at semver.org, don't rely on 'semver.valid(x) === x' as a round-trip check (build metadata makes that comparison fail on valid input) or on 'semver.valid(x) !== null' alone (accepts 'v1.2.3'). The 'semver' package IS the right tool for validRange()/range satisfaction/comparison — just not for strict version-format validation.
- capabilities and depends_on are both optional at the manifest level (default to {}/empty arrays) — a leaf plugin with no dependencies and nothing to declare is a valid, common case (e.g. a minimal plugin under active early development). id, version, and entry_point remain always-required.
- .strict() is applied at every nested object level (top-level manifest AND the capabilities object) so an unknown field anywhere — not just at the root — fails validation; the unrecognized_keys zod issue lands at the containing object's path with a root-relative '(root)' or 'capabilities' path (not per-key), which is reflected in how tests assert on it (checking issue.code === 'unknown_field' rather than a specific path).
- Next natural consumer: the plugin registry/loader (spec.md: 'discovers plugins under src/plugins/*, topologically sorts by depends_on, validates manifests, instantiates in dependency order') will call validateManifest() per plugin.json on disk and can reuse ValidationError's Result-style failure path; it will also need semver.satisfies()-style resolution against actually-installed plugin versions using the same 'semver' package now wired in here, plus detecting *circular* depends_on (this feature only validates grammar/shape, not the dependency graph's structure — that's the loader's job).
