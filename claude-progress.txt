## 2026-08-16 17:02 — Feature #1: Core error taxonomy and Result-style types for the kernel

### What was done:
- Added src/core/errors.ts: abstract AppError base class (extends Error) with a stable machine-readable code, a default HTTP statusCode, a safe overridable publicMessage (separate from the internal Error#message), optional structured details, and an internal-only cause (never serialized). Four concrete subclasses: ValidationError (400/VALIDATION_ERROR), ConfigError (500/CONFIG_ERROR), PluginLoadError (500/PLUGIN_LOAD_ERROR), CapabilityDeniedError (403/CAPABILITY_DENIED), each with its own safe default public message.
- toJSON({ includeStack }) serializes to an API error envelope shape { code, message, details?, stack? } — stack omitted unless includeStack is explicitly passed. Added isAppError() type guard and toErrorEnvelope(error, options) to collapse any unknown thrown value (plain Error, thrown string, etc.) into a generic non-leaking INTERNAL_ERROR envelope for the kernel's top-level error isolation path.
- Added src/core/types.ts: Result-style type (Ok<T> | Err<E>, default E = AppError) plus ok(), err(), isOk(), isErr(), unwrap(), unwrapOr(), mapResult(), mapErr() helpers for kernel operations that fail without throwing.

### Testing:
- tests/core/errors.test.ts (24 cases): per-subclass code/statusCode assertions, default public messages proven not to contain injected internal secrets/identifiers, explicit publicMessage override, internal message vs publicMessage independence, structured details round-trip, cause kept internal-only and absent from JSON.stringify output, toJSON() envelope shape exact-match with no stack key by default, stack included only when includeStack:true, toErrorEnvelope() behavior for AppError/plain Error/thrown string.
- tests/core/result.test.ts (9 cases): ok/err construction + isOk/isErr narrowing, unwrap returning value vs throwing the wrapped error, unwrapOr fallback, mapResult/mapErr transforming the correct branch and passing the other through untouched.
- Ran npm run build (tsc strict, incl. exactOptionalPropertyTypes/noUncheckedIndexedAccess) — clean. npm run lint (eslint) — clean. npm test (vitest) — 3 files / 33 tests passing (includes pre-existing smoke test). npx prettier --check on all new/changed files — clean.

### Notes:
- Kept AppError abstract so every thrown instance is forced through a concrete subclass with a real code; add new error kinds by extending AppError with a fixed code/statusCode and an overridden defaultPublicMessage(), not by instantiating AppError directly.
- publicMessage is intentionally separate from Error#message: message can carry internal detail for logs (file paths, plugin ids, SQL fragments) since it is never included in toJSON(); only publicMessage/code/details cross the API boundary.
- cause uses the native ES2022 Error cause option (supported by tsconfig lib ES2022) and is deliberately excluded from toJSON()/serialization — read it via error.cause for internal diagnostics/log correlation only.
- Result<T, E = AppError> lives in types.ts (not errors.ts) per spec.md's directory layout, and imports AppError only for the default type parameter — no runtime coupling.
- Gotcha for future agents: passing a variable already typed as the Result<T,E> alias into mapResult/mapErr can make TS fail to infer the callback parameter type (falls back to unknown) even though passing ok()/err() calls directly infers fine — annotate the callback parameter explicitly in that case (see result.test.ts) rather than trying to force generic type args onto ok()/err(), which only take one type parameter each.
- Next natural consumer: feature #4 (plugin manifest zod validator) will want ValidationError; api-gateway (later) will want toErrorEnvelope()/AppError#toJSON() for its error-envelope middleware.

## 2026-08-16 17:08 — Feature #2: Layered configuration system (defaults -> env -> operator overrides) validated with zod

### What was done:
- Added src/core/config.ts: generic loadConfig(schema, {defaults, env, overrideFilePath}) engine that merges three layers (defaults -> process.env -> optional local JSON override file) in that precedence order and validates the merged object with a zod schema, matching spec.md's 'validated per-plugin against a zod schema the plugin exports'. Env values are filtered to only the schema's own keys (via schema.shape) before merging, so process.env's hundreds of unrelated vars never leak in. The override file is fully optional — a missing path/file is a silent no-op, not an error; malformed JSON or a non-object top level throws ConfigError.

Full ZodError issues are attached as ConfigError.details for programmatic consumers, and the original ZodError is preserved as cause. ConfigError's default publicMessage ('The server is misconfigured.') deliberately never includes the internal field-level detail.
- Added config.local.json to .gitignore as the documented convention for the operator override file, alongside .env.

### Testing:

## 2026-08-16 17:18 — Feature #3: Structured logger with automatic secret redaction

### What was done:
- Added src/core/logger.ts: createLogger({ level, context, stream }) wraps pino to emit structured ndjson with a base context (pid, hostname, plus caller-supplied fields like plugin/requestId) merged into every line; withContext(logger, context) derives a child logger that layers further context (e.g. per-request requestId) on top without losing the parent's.
- Implemented deep, unconditional secret redaction: redactSecrets()/redactValue() recursively walk any object/array (with circular-reference guarding via WeakSet) and replace the value of any key matching REDACTED_FIELD_NAMES (password, secret, token, apikey, authorization — case/punctuation-insensitive substring match, so API_KEY, apiKey, x-api-key, accessToken, Authorization all match) with REDACTED_PLACEHOLDER ('[REDACTED]'). Wired in at three points so nothing bypasses it: base context passed to createLogger(), bindings passed to withContext()/child(), and every individual log call's merging-object/Error argument via pino's hooks.logMethod (which fires for child loggers too, confirmed empirically).
- Special-cased Error values: redactError() clones via Object.create(prototype) to preserve the original class (so pino's err serializer still reports the correct type, e.g. ValidationError/UpstreamError) and message/stack, while redacting any secret-like own enumerable property (e.g. a mistakenly attached err.apiToken); cause is intentionally dropped from the clone rather than redacted imperfectly. Left Date/RegExp/Map/Set/typed-arrays/Buffer and any value exposing its own toJSON() untouched (returned as-is) so redaction never corrupts values that manage their own JSON representation.

### Testing:
- tests/core/logger.test.ts (28 cases) using an in-memory Writable capturing stream (pino writes to it synchronously, confirmed empirically) so tests assert on the exact raw ndjson pino would emit, not a mock: structured JSON output with plugin/request context merged in (createLogger context, withContext layering, per-call fields alongside persistent context); redaction proven for all 5 field names across case/punctuation variants (password/Password/PASSWORD/userPassword, secret/clientSecret, token/accessToken, apikey/apiKey/API_KEY/x-api-key, authorization/Authorization) both via raw-string absence of the secret value (raw().not.toContain(secretValue)) and via the parsed line showing REDACTED_PLACEHOLDER; secrets nested arbitrarily deep in objects/arrays; a secret-like property attached to a thrown Error while message/stack/type are preserved; secrets in base context and in withContext() bindings; secrets never leak across repeated calls on the same logger. Plus direct unit coverage of redactSecrets(): every declared field name, non-secret fields untouched, input not mutated, circular references handled, Date and custom-toJSON values left opaque.
- Ran npm run build (tsc strict) — clean. npm run lint (eslint) — clean. npm test (vitest) — 5 files / 74 tests passing (28 new + pre-existing 46). npx prettier --check on the two new files — clean (pre-existing AGENTS.md/feature_list.json/spec.md warnings are unrelated/pre-existing, per feature #2's notes).

### Notes:
- Deliberately did NOT use pino's native path-based redact option (fast-redact) as the primary mechanism — it requires the caller to enumerate exact paths in advance (e.g. 'req.headers.authorization'), which can't guarantee an arbitrary, unknown-shape log call is safe. Instead built a recursive deep-redact walk keyed purely on field *names*, wired in via pino's hooks.logMethod (verified this hook receives the raw, pre-serialization first argument — including a raw Error before pino's internal err-wrapping — and that it fires on child loggers too, not just the root logger) plus explicit redaction of context/bindings at createLogger()/withContext() call sites (which bypass hooks.logMethod entirely since they aren't a 'log method call').
- Key design tradeoff future agents should know: redactValue() only reconstructs plain objects, arrays, and Errors; anything with its own toJSON() (or Date/RegExp/Map/Set/typed arrays) is returned untouched rather than descended into, so a class instance with a custom toJSON isn't corrupted by losing its custom serialization — but this also means a secret-like field nested *inside* a custom-toJSON object's internals would not be redacted. This is an intentional, documented scope boundary, not an oversight.
- Next natural consumers: the kernel's Capability/Permission Broker and RBAC plugin's audit log (spec.md: 'every capability grant, permission check, and mutating action is logged with actor/target/outcome') should use withContext() to attach actor/target/outcome fields; api-gateway's Fastify bootstrap should replace the placeholder 'logger: true' in src/server/index.ts with createLogger()/loadCoreConfig()'s LOG_LEVEL once the kernel bootstrap feature lands, so request logs get the same redaction guarantee instead of Fastify's bare pino default.

## 2026-08-16 17:24 — Feature #4: Plugin manifest schema (plugin.json) and zod validator

### What was done:
- Added src/core/manifest.ts: PluginManifestSchema (zod, .strict() at every object level) defining plugin.json's shape per spec.md — id (lowercase-kebab-case, regex-validated), version (canonical SemVer 2.0.0 grammar via a strict regex matching semver.org's own reference regex — deliberately NOT semver.valid(), which is a loose parser that accepts a 'v' prefix and silently strips build metadata from its output), depends_on (Record<pluginId, semverRange>, defaults to {}, validated with the 'semver' package's validRange() since range grammar — comparator sets, hyphen ranges, x-ranges, ||, — is impractical to hand-roll correctly as a regex), capabilities.provides/capabilities.requires (string arrays following a 'namespace:action' grammar, e.g. db:query/http:route/rbac:check, each defaulting to [], with a superRefine pass that flags duplicate entries within a single list — cross-list overlap between provides and requires is explicitly allowed), and entry_point (relative path regex: no leading '/', no '..' traversal, must end in .ts/.js/.mjs/.cjs).
- Added validateManifest(input: unknown): Result<PluginManifest, ValidationError> — never throws; uses schema.safeParse() (which does not short-circuit) so every violation in the input, not just the first, is collected into a typed ManifestValidationIssue[] ({ path, code, message }) and attached at ValidationError.details.issues, with a human-readable summary of all violations as the internal message (publicMessage stays the generic 'The request was invalid.' from errors.ts, so manifest content never leaks to an API caller). Custom zod issues (duplicate capability) and .strict()'s unrecognized_keys are both mapped to stable machine-readable codes ('duplicate_capability', 'unknown_field') alongside zod's own issue codes.
- Added 'semver' (^7.8.5) as a direct dependency (previously only present transitively) and '@types/semver' as a devDependency — used for depends_on range validation only; version format validation uses a hand-matched official regex instead, see Notes.

### Testing:
- tests/core/manifest.test.ts (36 cases): 7 valid-manifest cases (full manifest, minimal manifest with depends_on/capabilities defaulted, multi-segment id, prerelease+build-metadata version, a spread of valid range syntaxes — ^, ~, >=..<, x-range, '*' — in depends_on, nested entry_point path, empty provides/requires arrays); bad semver (5 variants: '1.2', 'not-a-version', '1.2.3.4', 'v1.2.3', '' via it.each, plus a dedicated case asserting the error names the 'version' path and publicMessage stays generic); missing id (field entirely absent, and empty-string id); duplicate capability (within provides, within requires, plus a case proving the same capability in both provides AND requires is NOT flagged as duplicate); malformed capability grammar (7 variants via it.each: no colon, empty action segment, empty namespace segment, double colon, 3+ segments, uppercase, space-instead-of-colon); unknown field (top-level, and nested under capabilities); plus additional invalid variants covering malformed depends_on range, uppercase/underscore plugin id, absolute and directory-traversal entry_point, unsupported entry_point extension, non-object input, missing entry_point, and one case asserting ALL violations in a single malformed manifest are collected (not just the first).
- Ran npm run build (tsc strict) — clean. npm run lint (eslint) — clean. npm test (vitest) — 6 files / 110 tests passing (36 new + pre-existing 74). npx prettier --check on the two new/changed files — clean.

### Notes:
- Chose depends_on as Record<pluginId, semverRange> (mirrors package.json#dependencies) rather than an array of {id, range} objects — cleaner JSON shape, and it structurally rules out duplicate dependency entries for free (JS/JSON object keys are unique), so the 'duplicate' requirement in this feature's steps only needed custom superRefine logic for capabilities.provides/requires, which ARE meaningful ordered lists where duplicates are a real, detectable mistake.
- Gotcha for future agents: semver.valid(value) is NOT a strict/canonical-format check — it's lossy (drops build metadata) and lenient (accepts a leading 'v'). If you need to validate that a string IS canonical SemVer 2.0.0 (not just parseable-ish), match it against the official regex published at semver.org, don't rely on 'semver.valid(x) === x' as a round-trip check (build metadata makes that comparison fail on valid input) or on 'semver.valid(x) !== null' alone (accepts 'v1.2.3'). The 'semver' package IS the right tool for validRange()/range satisfaction/comparison — just not for strict version-format validation.
- capabilities and depends_on are both optional at the manifest level (default to {}/empty arrays) — a leaf plugin with no dependencies and nothing to declare is a valid, common case (e.g. a minimal plugin under active early development). id, version, and entry_point remain always-required.
- .strict() is applied at every nested object level (top-level manifest AND the capabilities object) so an unknown field anywhere — not just at the root — fails validation; the unrecognized_keys zod issue lands at the containing object's path with a root-relative '(root)' or 'capabilities' path (not per-key), which is reflected in how tests assert on it (checking issue.code === 'unknown_field' rather than a specific path).
- Next natural consumer: the plugin registry/loader (spec.md: 'discovers plugins under src/plugins/*, topologically sorts by depends_on, validates manifests, instantiates in dependency order') will call validateManifest() per plugin.json on disk and can reuse ValidationError's Result-style failure path; it will also need semver.satisfies()-style resolution against actually-installed plugin versions using the same 'semver' package now wired in here, plus detecting *circular* depends_on (this feature only validates grammar/shape, not the dependency graph's structure — that's the loader's job).

## 2026-08-16 17:30 — Feature #5: Plugin directory discovery and scanning

Each PluginScanEntry pairs the directory (name, directoryPath, manifestPath) with the raw, UNVALIDATED parsed manifest (unknown) — validation against PluginManifestSchema stays manifest.ts's job (feature #4's validateManifest()), not scanned here, per spec.md's registry/loader split.

## 2026-08-16 17:37 — Feature #6: Dependency graph resolution: topological sort, semver range checks, cycle detection

### What was done:
- Added src/core/graph.ts: buildDependencyGraph(manifests) indexes an array of already-validated PluginManifest values (feature #4's validateManifest() output) into a DependencyGraph keyed by plugin id (id -> {id, version, dependsOn}) — pure data transformation, first manifest wins on an id collision. resolveLoadOrder(manifests) is the module's single entry point: builds the graph, then (1) collects ALL edge issues in one pass — duplicate_plugin_id (two manifests declaring the same id), missing_dependency (a depends_on id that wasn't discovered), version_range_mismatch (semver.satisfies() fails against the discovered dependency's version) — returning Err(PluginLoadError) with every issue attached at error.details.issues if any exist; (2) only once every edge resolves, runs DFS-based cycle detection (findCycle) which reconstructs and returns the exact cycle path (e.g. ["a","b","c","a"]) via a white/gray/black visited-state stack, returning Err(PluginLoadError) naming the cycle both in the message ("a -> b -> c -> a") and at error.details.cycle if one is found; (3) only once acyclic, runs topologicalSort — Kahn's algorithm with the ready-queue kept sorted lexicographically by id at every step — so the result is a deterministic Ok(string[]) load order (dependencies always precede dependents) regardless of input array order or which valid ordering the graph admits (diamonds, unrelated plugins).

### Testing:
- tests/core/graph.test.ts (25 cases): buildDependencyGraph unit coverage (indexes correctly, first-wins on duplicate id, empty input); linear chain (a<-b<-c) resolved correctly and proven order-independent of input array order; diamond dependency (d depends on b+c, both depend on a) resolved with a first/d last plus explicit indexOf ordering assertions, and a separate determinism case for unrelated plugins (lexicographic tie-break); missing dependency (single case asserting message + issue shape, plus a multi-issue case proving every missing dependency is collected, not just the first); version range mismatch (rejected case asserting message contains plugin/dependency/range/installed-version, plus an accepted case proving a satisfying range passes); duplicate plugin id rejected; circular dependency: the required 3-node cycle (a->b->c->a) with message asserted to contain both "Circular dependency" and the exact "a -> b -> c -> a" path, a rotation-invariance case (same cycle reported regardless of which node appears first in the input array), a direct self-dependency (a->a) one-node-cycle edge case, and a case proving the cycle is still found correctly when unrelated acyclic plugins are also present in the graph; empty-manifest-set returns an empty load order.

### Notes:
- resolveLoadOrder() takes readonly PluginManifest[] (feature #4's validated type) — it does not scan the filesystem or read raw/unknown manifests (that's registry.ts, feature #5) and does not instantiate plugins or run lifecycle hooks (that's loader.ts, feature #8, which depends_on [6,7] and will call resolveLoadOrder() then feed the returned order + feature #7's capability broker into instantiation).
- Followed manifest.ts's established Result-style precedent for expected/recoverable failures (collect every issue via safeParse-style aggregation, not fail-fast on the first) rather than errors.ts's throw-style precedent (reserved for genuine kernel misconfiguration like registry.ts's missing plugins-root) — a broken dependency graph is data the caller (the future loader) needs to inspect/log/decide policy on, not an unrecoverable process-level fault.
- Added duplicate_plugin_id detection (not explicitly required by this feature's steps, but a natural extension of 'build a dependency graph from discovered manifests' since registry.ts scans by directory name, not by manifest id — two directories could legally declare the same id) — kept cheap and consistent with the existing 'collect every issue' pattern rather than treated as a special case.
- Cycle detection intentionally runs AFTER edge-issue collection and returns early on edge issues, so a graph with an unresolvable edge is never also reported as cyclic (unresolvable edges are structurally excluded from cycle traversal in findCycle) — keeps each Err's details focused on one class of problem at a time, matching how a future loader would want to branch on error.details.
- topologicalSort()'s ready-queue is kept sorted (splice-insert on decrement, not re-sorted from scratch every iteration) purely for readability/determinism, not because O(n log n) matters at plugin-count scale (dozens, not thousands) — correctness > micro-optimization here, consistent with the kernel's other feature notes.
- Next natural consumer: feature #8 (plugin loader) — call scanPluginDirectories() (feature #5) -> validateManifest() per entry (feature #4, likely skip-and-log invalid manifests per feature #5's notes) -> resolveLoadOrder() on the validated set -> instantiate each plugin in the returned order, granting capabilities via feature #7's broker as it goes. If the loader wants graceful partial-load behavior (skip only the plugins affected by a bad edge/cycle rather than failing the whole boot), it will need to post-process DependencyIssue[]/the cycle array itself — resolveLoadOrder() deliberately treats the graph as all-or-nothing since that policy call belongs to the loader, not here (mirrors feature #5's registry/loader split precedent).

## 2026-08-16 17:45 — Feature #7: Capability broker: declare, grant, and revoke inter-plugin capabilities

### What was done:
- Added src/core/broker.ts: createCapabilityBroker() factory (no exported singleton — module exports only the factory function at runtime) implementing the three lifecycle verbs: declareRequirement()/declareRequirements() record a plugin's capabilities.requires; registerProvider() lets a provider plugin register an implementation (function or object) for a capability id, rejecting a second, different plugin from registering the same id (no hijacking); grant()/revoke() are the operator-facing authorization step — grant() only succeeds if the plugin declared the capability (declares.requires is the ceiling, per spec.md), independent of whether a provider exists yet; revoke() is immediate and permanent for already-issued handles.
- obtain(pluginId, capabilityId) is the single gate: succeeds only when all three conditions hold — declared, granted, and a provider is currently registered — otherwise returns Err(CapabilityDeniedError) with a machine-readable details.reason (not_declared | not_granted | no_provider). forPlugin(pluginId) returns a narrow PluginCapabilityAccess facade exposing only a pre-bound obtain(capabilityId) — this is what a future loader (feature #8) should inject into plugin instances instead of the full broker, so plugin code never has grant/revoke/registerProvider power over itself or anyone else.
- Immediate revocation is implemented via a per-grant mutable GrantRecord ({ live: boolean }) that obtain() closes over when it wraps a handle in a Proxy (apply trap for function handles, get trap with method rebinding for object handles); revoke() flips that exact record's live flag to false (so already-issued handles throw CapabilityDeniedError on their very next call/property-access) and deletes the grants map entry so a later grant() mints a brand-new record — an old revoked handle can never be resurrected by a subsequent re-grant. Primitive handles (string/number/etc.) are returned unwrapped, documented as an intentional scope boundary (JS has no hook to intercept reads of an already-copied primitive).

### Testing:
- tests/core/broker.test.ts (25 cases) across 4 describe blocks matching the feature's 3 required scenarios plus the 'no ambient access' architectural requirement: granted-capability-usable (function handle call-through, object handle with preserved 'this', isGranted() true, forPlugin() facade parity, bulk declareRequirements()); undeclared-request-denied (obtain and grant() both denied not_declared, not_granted when declared-but-not-granted, no_provider when granted-but-unprovided, cross-capability and cross-plugin isolation, registerProvider() hijack rejection returning PluginLoadError); revoked-stops-immediately (a held function handle throws on its next call right after revoke() with no re-obtain needed, same for an object handle's method, obtain()-after-revoke denied not_granted, isGranted() flips false, re-grant produces a working NEW handle while the OLD pre-revoke handle stays permanently dead, revoke() on a never-granted capability is a no-op); no-ambient-access (dynamic import of broker.ts shows only createCapabilityBroker as a runtime export, two broker instances have fully independent state, forPlugin() facade's own keys are exactly ['obtain'], a facade bound to one plugin cannot reach a capability declared/granted to a different plugin, no getProvider()/providers escape hatch exists on the broker object).
- Ran npm run build (tsc strict, incl. exactOptionalPropertyTypes/noUncheckedIndexedAccess) — clean. npm run lint (eslint) — clean. npm test (vitest) — 9 files / 166 tests passing (25 new + pre-existing 141). npx prettier --check on both new files — clean (auto-fixed one formatting pass first).

### Notes:
- broker.ts deliberately depends only on errors.ts/types.ts (feature #1/#2, matching this feature's depends_on) and NOT manifest.ts — it treats capability ids and plugin ids as plain strings, trusting that manifest.ts's PluginManifestSchema (feature #4) already validated the 'namespace:action' grammar upstream. The future loader (feature #8, depends_on [6,7]) is expected to call declareRequirements(manifest.id, manifest.capabilities.requires) and registerProvider(manifest.id, capabilityId, impl) per plugin.capabilities.provides during instantiation, then have an operator/admin surface call grant()/revoke() — this module only provides the primitive, it doesn't decide load-order policy (consistent with graph.ts's and registry.ts's precedent of staying a pure, standalone primitive).
- Key design decision: grant() checks 'declared' but deliberately does NOT require a provider to already be registered — this lets an operator pre-authorize a plugin before its dependency has finished loading (boot-order flexibility), while obtain() is the one place all three conditions (declared + granted + provider-present) are checked together, matching this feature's step 1 wording literally ('can only obtain a capability handle it declared...and that is registered by a provider') as the obtain-time gate, with 'granted' as the third leg implied by the feature title's three verbs and spec.md's 'declared...and that the operator has granted'.
- Revocation correctness hinges on obtain() closing over the SAME GrantRecord object across every handle minted under one grant, and revoke() both flipping that object's live flag (kills already-issued handles) AND deleting the map entry (so a later grant() call constructs a fresh GrantRecord rather than reusing/reviving the old one) — reusing the same object across a revoke->grant cycle would have been a bug (old handles would silently start working again); this was deliberately tested (re-grant after revoke: old handle stays dead, new handle from a fresh obtain() call works).
- 'No ambient/global way to reach another plugin's internals' (step 2) is enforced structurally, not just documented: broker.ts has zero module-level mutable state and exports no singleton (verified by test: dynamic-importing the module shows only createCapabilityBroker as a key), and forPlugin()'s returned facade is Object.frozen with exactly one method (obtain, pre-bound to that plugin's own id) — there is no parameter or method anywhere on that facade that lets a plugin address a different plugin's identity or list/enumerate other plugins' providers.
- Next natural consumer: feature #8 (plugin loader) wires resolveLoadOrder()'s output (feature #6) together with this broker — for each plugin id in load order, call declareRequirements() from its validated manifest, instantiate the plugin (passing it broker.forPlugin(id) as its only capability-facing handle), then call registerProvider() for whatever capabilities.provides it offers so later-loaded consumers can be granted access to it.

## 2026-08-16 17:56 — Feature #8: Plugin loader: instantiate plugins in dependency order and run lifecycle hooks

### What was done:
- Added src/core/loader.ts: loadPlugins(definitions, broker, options?) instantiates plugins in dependency order (calls graph.ts's resolveLoadOrder() internally on the definitions' manifests — 'the sorted graph' is produced here, not passed in separately). Per plugin id in that order: declareRequirements() with the broker, registerProvider() for every capabilities.provides entry (erroring clearly if the module's provides map is missing an implementation the manifest promised, or if a different plugin already registered that capability id — broker.ts's hijack rejection), then decides which declared capabilities to broker.grant() via a pluggable GrantPolicy (default export grantAllDeclared(): grants everything declared — broker.ts's docs frame grant() as an 'operator/admin surface' concern, so this default is intentionally overridable via options.grantPolicy for a future kernel bootstrap backed by real RBAC/config), then calls onInstall(context) then onEnable(context) (awaited in sequence) with context = { manifest, capabilities: broker.forPlugin(id), logger }, before moving to the next plugin.

## 2026-08-16 18:02 — Feature #9: Typed event bus for cross-plugin publish/subscribe

### What was done:

Once a process's 64KB OS pipe buffer fills with the CLI's verbose tool-output streaming, its writes block -- a textbook Python subprocess pipe-deadlock. Confirmed via macOS's unified log (`log show`): all 3 claude PIDs for the failing batch started simultaneously at 21:02:56 and all exited cleanly (not signal-killed) with code 1 and zero stderr after ~38-43s -- too short for real feature work, long enough to fill a pipe buffer with init.sh's noisy docker/npm/build/test output. Lighter earlier batches (#31/#45/#12) produced less output and never crossed the threshold, which is why they succeeded while this heavier trio (both involving docker-compose MySQL via feature #18) didn't.
- Fixed run_parallel_batch() (dev-agent.py) to redirect each subprocess's stdout+stderr to a per-feature log file under .autopilot-logs/ instead of an unread PIPE, and swapped the sequential proc.communicate() drain loop for proc.wait() + reading the log file after exit. This removes the deadlock entirely and, as a side benefit, leaves full untruncated per-feature session logs on disk for future debugging (the original diagnostic session was hamstrung by dev-agent.py only ever printing stderr[:300]).

### What was done:
- Added src/plugins/html-renderer/src/escape.ts: four context-specific escapers — escapeHtml (HTML body/text, encodes & < > " '), escapeAttr (HTML attribute value, quoted or unquoted — hex-entity-encodes every non-alphanumeric char per OWASP Rule #2, safe regardless of quoting style), escapeUrl (URL-bearing attributes — strips embedded ASCII control/space chars, rejects any value whose scheme doesn't match an http(s)/mailto/ftp/tel/relative-URL allowlist by replacing it with an inert 'about:invalid#...' placeholder, then attribute-escapes what remains), and escapeJs (JS string-literal context inside <script> or an on*= handler — encodes every non-alphanumeric char as \\xHH/\\uHHHH). escapeForContext(value, context) dispatches to the right one.
- Added src/plugins/html-renderer/src/html-context.ts: annotateEscapeContexts(nodes), a compile-time HTML-tokenizer state machine that replays every TextNode's literal text in AST source order and records which of the 4 contexts each VariableNode landed in — HTML body text, an attribute value (further split into url/js/plain-attr by attribute name: href/src/action/... -> url, on*= -> js, else -> attr), or <script> body -> js. {{#if}}/{{#each}} branches are scanned from a cloned state and never write back into the parent scanner state (well-formed templates open/close tags within one branch/loop body, so this is exact for real templates and fails safe — never laxer — for malformed ones).

### Notes:
- escapeAttr and escapeUrl are deliberately aggressive (hex-encode every non-alphanumeric character) rather than only escaping & < > " ' — this is intentional per OWASP XSS Prevention Rule #2: the compiler cannot statically guarantee an attribute is quoted at the point escapeForContext() runs (the escaper itself only receives the string value and a context label, not quote-style), so the safe choice is an encoding that is correct for double-quoted, single-quoted, AND unquoted attribute values alike. The trade-off is that benign URLs/attribute text come out visually re-encoded (e.g. 'https://x.com' -> 'https&#x3A;&#x2F;&#x2F;x.com') rather than pass-through-readable; this is still byte-for-byte the same URL after the browser's standard HTML-entity decoding, so it is not a functional regression, only a readability one. Tests that need to assert exact output for such values import escapeAttr from escape.ts directly and build the expected string, rather than hardcoding a literal that would drift from the escaper's actual behavior.
- The HTML-context scanner in html-context.ts is deliberately not a full HTML5 tokenizer — no DOCTYPE/CDATA/RCDATA, no error-recovery beyond 'stay put and keep scanning', comments are skipped but any interpolation found inside one falls back to 'html' escaping (documented limitation, not a required context per this feature's steps). Interpolating into a tag name or attribute *name* position (<{{tag}}>, <div {{attr}}="x">) also has no safe generic escaper and conservatively falls back to 'html' — see the module's 'Contexts not modeled' doc section.
- URL_ATTR_NAMES (href, src, action, formaction, cite, poster, background, data, longdesc, manifest, srcset) and the on*-prefix event-handler check are a reasonable, commonly-used allowlist, not the full HTML living-standard list — extend these sets first if a future feature needs a URL/JS attribute this doesn't yet cover.
- Feature #50 (an explicit raw/unescaped-output helper) is the ONLY sanctioned way a future feature may add an opt-out from this escaping — do not add one ad hoc; this feature's step 2 ('no way to accidentally opt out') is a hard requirement of the current template syntax.
